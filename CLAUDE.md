# Gondola — CLAUDE.md

Gondola is a CLI tool (`gondola-cli`) that scaffolds and manages FastAPI projects
("convention over configuration" for the FastAPI/async ecosystem). This file
is auto-loaded by Claude Code at the start of every session in this repo.

## What this repo is (and isn't)

This is the **Gondola CLI tool itself** — not a generated FastAPI project.
Its job is to generate other people's FastAPI projects (models, routers,
services, mailers, migrations, seeds, tests) via `gondola init` / `gondola g ...`.
Keep that distinction in mind: changes here affect what *other* projects look
like after scaffolding, so template/generator code needs extra care.

## Stack

- Python 3.12+, Poetry for dependency management
- Default generated stack: SQLModel + asyncpg + Alembic (Postgres), with
  MySQL/MariaDB (asyncmy) and SQLite (aiosqlite) as alternatives
- Optional Postgres extensions: postgis, pgvector
- Rich for CLI output
- pytest for tests (unit + integration), mypy for type checking

## Commands Claude should know

```bash
poetry install                # install deps
poetry run pytest             # run full test suite
poetry run pytest test/unit   # unit tests only
poetry run pytest test/integration
poetry run mypy .             # type check
poetry run gondola --help     # exercise the CLI locally
poetry build                  # build sdist + wheel
poetry publish                # publish to PyPI (NEVER run without explicit human confirmation)
```

## Conventions

- Generated project layout (what `gondola init` produces) is documented in
  README.md — don't change the scaffolded directory structure without
  updating both the generator code and the README's "What gets created?" tree.
- Every generator (`model`, `router`, `service`, `mailer`, `seed`) must keep
  producing a matching test file — this is a core project promise, not optional.
- Project names generated by `gondola init` are normalized to
  `lowercase-with-hyphens`.
- API versioning in generated PostgreSQL projects is **header-based**
  (`API-Version: v1`), not URL-prefix based — don't "fix" this to path
  versioning without discussing it first, it's an intentional design choice.
- Command aliases matter and must stay in sync: `init`/`i`, `start`/`s`,
  `generate`/`g`, `delete`/`d`, `db seed`/`db s`, `db clear`/`db c`,
  `db destroy`/`db d`, `migrate history`/`migrate h`, `migrate current`/`migrate c`.

## Workflow expectations

- Run the relevant test suite after any code change before considering a task done.
- For changes to generators, prefer adding/updating a test that actually runs
  `gondola generate ...` against a temp project and asserts on the output files,
  not just unit-testing the template string.
- For migration/Alembic-related changes, be extra careful — these touch
  irreversible-by-default database operations in *generated* projects.
- Never run `poetry publish`, `twine upload`, destructive `db destroy`/`db clear`
  commands, or `git push` without explicit confirmation in that session, even
  if a permission rule would technically allow it.
- Follow existing docstring/type-hint style (full mypy support is a stated
  feature — don't introduce untyped code).

## Release process (for reference — always confirm with the human before executing any step)

1. Bump version in `pyproject.toml`
2. Update CHANGELOG if present
3. `poetry run pytest` — full suite must pass
4. `poetry build`
5. `poetry publish` (or `twine upload dist/*`) — requires PyPI credentials,
   never stored in this repo or committed to git
6. Tag the release in git and push tags
