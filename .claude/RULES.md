# RULES.md — Gondola Agent Rules

These are hard operating rules for any AI agent (Claude Code or otherwise)
working in this repository. Follow them exactly, every session.

## 1. Environment

- **Always activate the virtualenv before running any command**, using:
  ```bash
  workon gondola
  ```
  Run this as the first command of every session and again after any shell
  restart. Do not run `poetry run`, `pytest`, `mypy`, `ruff`, `gondola`, or
  any other project command without the `gondola` virtualenv active.
- If `workon gondola` fails (environment doesn't exist yet), stop and tell
  the human — do not create a new environment under a different name or
  fall back to system Python.

## 2. Testing

- Run the test suite before considering any code change complete:
  ```bash
  poetry run pytest --cov
  ```
- Prefer running the narrowest relevant subset while iterating
  (`poetry run pytest test/unit/models`), but run the full suite before
  declaring a task done.
- Changes to generators (`gondola generate ...`) should be verified by
  actually running the generator against a temp project and asserting on
  output files, not just by unit-testing template strings in isolation.

## 3. Linting and type checking

- Run both before finishing any task that touches Python code:
  ```bash
  poetry run ruff check .
  ```
- Fix lint/type errors rather than suppressing them (`# type: ignore`,
  `# noqa`) unless there's a genuine, documented reason — leave a comment
  explaining why if you do suppress one.

## 4. Commits and versioning

- This project uses **conventional commits** (`feat:`, `fix:`, `chore:`,
  `docs:`, `refactor:`, `test:`, etc.) — commitizen relies on these prefixes
  to determine version bumps and changelog entries. Use them for every commit.
- Never hand-edit the `version` field in `pyproject.toml`. Version bumps are
  handled by `cz bump` in CI when a PR targets `main` — do not do this
  manually or as part of a feature PR.
- Never hand-edit `CHANGELOG.md`. It's generated by commitizen.

## 5. Things that require explicit human confirmation

Never run these without the human explicitly confirming in the current
session, even if a permission setting would technically allow it:

- `poetry publish` / `twine upload` (publishing to PyPI)
- `git push`, `git push --tags`
- `gondola db destroy`
- `gondola db clear`
- `gondola migrate down` / `alembic downgrade`
- Any `git commit --amend` or `git rebase` on a shared/pushed branch
- Editing `.circleci/config.yml`, CI contexts, or anything holding secrets

## 6. Project-specific conventions

- This repo is the **Gondola CLI tool itself**, not a generated FastAPI
  project — changes to generator templates affect what other people's
  projects look like after scaffolding. Treat generator/template code with
  extra care.
- Every generator (`model`, `router`, `service`, `mailer`, `seed`) must keep
  producing a matching test file. This is a core project promise.
- API versioning in generated PostgreSQL projects is **header-based**
  (`API-Version: v1`), not URL-prefix based. Don't change this pattern
  without discussing it first.
- Command aliases must stay in sync with their full commands: `init`/`i`,
  `start`/`s`, `generate`/`g`, `delete`/`d`, `db seed`/`db s`,
  `db clear`/`db c`, `db destroy`/`db d`, `migrate history`/`migrate h`,
  `migrate current`/`migrate c`.
- Full type hints are required project-wide (mypy runs with
  `disallow_untyped_defs = true`) — don't introduce untyped code.

## 7. Secrets

- Never read, print, log, or commit `.env`, `.env.*`, `.pypirc`, or anything
  containing a token or credential.
- Never suggest storing PyPI or GitHub tokens directly in
  `.circleci/config.yml` or any file tracked by git — they belong in
  CircleCI contexts / environment variables only.

## 8. When in doubt

If a task is ambiguous, destructive, irreversible, or not clearly covered
by these rules, stop and ask rather than guessing.
